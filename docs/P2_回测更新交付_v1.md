## 3. 给 P3/P4 的门限接口

```python
apply_threshold(
    raw_action, threshold_mode, threshold_config, critic=None, *,
    obs=None, model=None, hmax=None, ordered_tickers=None, algorithm=None,
) -> (action, info)
```

- raw_action、obs为float32副本；raw_action已从单批维中取出并按股票顺序验证。输入配置每步深拷贝；不得在门限中训练模型或修改其权重/环境。
- 返回action严格为`(n,)`，保持float32坐标，范围`[-1,1]`，不能有NaN/Infinity。P2不静默截断或重排。
- info必须报告同一个`threshold_mode`。simple的`accepted`为`(n,)`布尔数组，critic为布尔标量；被拒绝动作归零，放行动作保持原值。
- critic可附`critic_policy_value`、`critic_zero_value`、`critic_delta`有限标量；P2只记录，不另选Critic摘要或阈值。
- 风险强平和可交易限制由环境最后执行。`threshold_accepted=false`并不保证该日完全没有卖出；风险规则可能覆盖零动作。
- 当前simple/critic仍抛`NotImplementedError`；P2测试使用假过滤器验证接入和错误路径，不能作为正式门限实现或收益结果。

门限实现当前位于runner.py，清单哈希覆盖整个该文件。若P3/P4拆为独立模块，须同步扩展实际实现源码的指纹，不应只记录调用代码。Critic的摘要、动作输入坐标、阈值、相等边界、无效值处理仍待P4登记；P2本次不代为决定。

## 5. 反馈和后续关口

1. **P1动作文件日期**：当前训练端`validation_actions.csv`只保存资产列，因为日期存在索引中而使用`to_csv(index=False)`。本次先用已核对账户日期和动作行顺序对比，并在报告显式标记。建议P1保存时保留date，以便跨机器独立核验，不必依赖另一文件恢复日期。
2. **P3/P4正式门限交付**：需采用上述返回格式并登记实现、配置与Critic规则；交付后再用真实规则验证临界取整、逐资产拒绝、整向量拒绝、价值对比和验证集候选汇总。未交付时执行会失败，不产生伪造的已完成结果。
3. **正式训练/测试关口**：P2汇总并不执行自动门限选优；P3/P4冻结选择规则，P5留存记录。全部门限和选中模型冻结后才运行24次正式测试。
